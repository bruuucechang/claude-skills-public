# 除錯：先有會紅的指令，才准提假設

> 改寫自 Matt Pocock 的 `diagnosing-bugs` 與 obra/superpowers 的 `systematic-debugging`。沒有整支照搬：跟這裡「開工後不回頭問」衝突的地方改掉了。

**最常見的失敗是讀程式讀出一個理論，就照理論改。** 理論可能是對的，但沒有一條會紅的指令，
改完也證明不了修好了——「看起來對了」跟原則 1「沉默不等於成功」是同一個坑。

## 第一步：做出會紅的指令（這一步就是整支 skill）

完成的判準：講得出**一條指令**（測試、curl、CLI＋fixture、headless 腳本），而且**已經跑過至少一次**、輸出貼在你的紀錄裡，並且：

- **會紅**：走到真的出問題的那條路，斷言的是**使用者講的那個症狀**，不是「沒崩潰」。抓不到這個 bug 的指令不算
- **每次結果一樣**：不穩定的 bug 改用統計判準——「跑 N 次失敗 ≥ k 次」算紅，先把重現率拉高（迴圈跑 100 次、加壓、縮時窗），50% 可以查，1% 不行；
  效能問題的紅＝量出來的時間超過記下的基準
- **幾秒跑完**：30 秒還時好時壞的迴圈幾乎等於沒有
- **不用人**：你能自己跑

讀程式找入口、接縫、fixture 是做指令的一部分，可以；**在這條指令出現之前就對「原因」下判斷、照判斷改程式——停。** 先做指令。

做法大致照這個順序試：失敗的測試 → 打開著的服務的 curl → CLI 餵 fixture 跟正確輸出 diff →
headless 瀏覽器腳本 → 把抓到的真實請求／事件存檔重播 → 拋棄式小 harness → 隨機輸入跑 1000 次 →
兩個版本之間 `git bisect run` → 新舊版本同輸入 diff。

**真的做不出來**：照實寫進回報——試了哪些、卡在哪、缺什麼（某台機器的環境、一份日誌、權限）。
缺的東西要使用者給（登入、他的機器、正式環境）才算重大事件，用選項問；其餘不要沒有指令就開始猜。

## 第二步：重現、縮小

- 確認紅的是**使用者描述的那個症狀**，不是旁邊另一個長得像的錯。抓錯 bug＝修錯地方
- 把重現一次刪一個元素（輸入、呼叫者、設定、步驟），每刪一個重跑一次；刪掉就變綠的才留下
- 縮到每個元素都不可少為止，這份最小重現之後就是回歸測試

## 第三步：列假設（寫進回報，不拿去問使用者）

- 測任何一條之前先列 **3～5 條、排好順序**——只列一條會被第一個想到的念頭綁住
- 每條都要能被推翻：「**如果原因是 X，那改 Y 症狀就會消失**」。講不出預測的是感覺，丟掉或磨尖
- 清單寫進回報（或交接單），**不跳框問使用者排序**：開工後不回頭問，照你的排序做下去

## 第四步：一次只動一個變數

- 每一個探針對應一條假設的預測。能下中斷點／REPL 就不要灑 log；不要「全部印出來再 grep」
- **除錯 log 一律加唯一前綴**（例如 `[DEBUG-a4f2]`），收尾一個 `grep -rn 'DEBUG-a4f2'` 就清得乾淨
- 效能問題先量基準（計時、profiler、query plan）再二分，不要先改

## 第五步：修＋回歸測試

1. 找得到**對的接縫**（測試走的是真實出錯的那條呼叫鏈）就先把最小重現寫成測試；接縫太淺的測試只給假安心——
   **找不到對的接縫本身就是發現**，寫進回報
2. **看它紅一次。** 修正已經寫好（甚至 commit 了）才補測試時，暫時退掉修正、不碰 index：
   ```bash
   K=<scratchpad>/keep; mkdir -p "$K"; cp <修正的檔…> "$K"/                 # 存一份修好的
   git show <修正前的 commit>:<檔> > <檔>                                   # 每個修正的檔寫回舊版；修正是新檔就先移到 $K
   <跑測試，看它紅>
   cp "$K"/<檔…> <原位置>; git status --porcelain                          # 蓋回；要跟退之前一模一樣
   ```
   `git stash push -- <檔>` 對已 commit 的修正是空操作、`git checkout <rev> -- <檔>` 會改到 index，都不要用；
   整片清的寫法 git-wipe-guard 會擋。用改程式或改 fixture 逼紅的，跟原版 `diff` 證明改動真的生效了，再相信那個紅
3. 修 → 看它綠 → 拿第一步那條原始指令（沒縮小的那份）再跑一次

修了兩輪還過不了就停止再改程式，回頭質疑前提（是不是架構本身的問題）：試過的假設與證據寫進回報；
只有符合重大事件（驗收失敗修不好）才用選項問使用者——跟 `blocks` 的「修兩輪過不了要停」同一條。

## 收尾（宣告修好之前全部要成立）

- [ ] 第一步那條指令現在是綠的（貼輸出）
- [ ] 回歸測試綠；或寫明為什麼沒有對的接縫
- [ ] `grep` 前綴，除錯 log 清光
- [ ] 拋棄式腳本刪掉，或放在明確標示的除錯位置
- [ ] **最後證實的那條假設寫進 commit／PR 訊息**，下一個除錯的人才學得到
- [ ] 回報裡附：那條會紅的指令（重跑用）、假設清單與哪條成立
